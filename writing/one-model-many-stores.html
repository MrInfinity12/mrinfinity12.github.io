One model, many stores: what a CPU-only computer vision system taught me

Thomas O'Beirne, October 7, 2026

For a pizza franchise group, I built PizzaQuality AI. A camera above the prep area in each store photographs every pizza, and a YOLOv8 model grades it against the recipe: toppings, crust, bubbles, and shape, scored out of 100. One model serves every store, and inference never needs a GPU. A Raspberry Pi in the store runs a small detector, and a rented server does the grading on its CPU.

This post covers what that setup taught me, and what I'd change if I built it again.

The shape of the system

The pipeline has three stages:

  1. Capture. A Raspberry Pi 5 in each store watches the prep area through an overhead camera at 4056 by 3040 pixels. A stock YOLOv8 nano model, filtered to the COCO pizza class, looks for a pizza. When one holds still for three consecutive frames (the center moves less than 50 pixels, the box area changes less than 30%, and the pizza fills at least 20% of the frame), the Pi crops it with 15% padding and saves a JPEG.
  2. Transport. A background thread uploads each crop to an S3-compatible bucket under <store>/<date>/<filename> and deletes the local copy after a successful upload.
  3. Grading. A Hetzner server pulls from the bucket every 15 minutes and runs two YOLOv8 nano segmentation models on its CPU: a 21-class pizza model and a hand model that blurs staff hands for privacy. Grading takes about 1.5 seconds per image. Results appear in a Streamlit dashboard behind a Cloudflare Tunnel, where store managers see their own store and the owner sees all of them.

Each stage is ordinary on its own. The lessons came from where they meet.

CPU was fast enough; memory wasn't

Speed wasn't the constraint. The Pi waits at least 6 seconds between captures, so 1.5 seconds of grading per image leaves plenty of headroom.

Memory was the constraint. Ultralytics keeps segmentation masks at the original image resolution, which came to about 30 MB per high-resolution image. A batch of 37 images peaked above 3.5 GB on a server with 4 GB of RAM, and the grading process was killed for running out of memory. The fix was to drop each result as soon as I had extracted the numbers, and to collect garbage between images:

import gc
from pathlib import Path

from ultralytics import YOLO

model = YOLO("best.pt")
for img_path in sorted(Path("images").glob("*.jpg")):
    result = model(str(img_path), device="cpu", verbose=False)[0]
    print(img_path.name, len(result.boxes))
    result = None  # full-resolution masks stay in memory until released
    gc.collect()

On a CPU-only box, measure memory per image as early as you measure time per image. The time budget was generous. The memory budget wasn't.

Give every device an identity before its first photo

The first capture code named files pizza_<timestamp>_conf-<confidence>.jpg. With one Pi, that was fine. With more than one Pi uploading to the same bucket, there was no way to tell which store a photo came from.

The fix was a store_id in each Pi's configuration, prefixed to every filename. The uploader splits the filename to build the object key, so photos land in a folder per store and per day. My retrospective notes from that sprint say it plainly: retrofitting identity later is painful. Any fleet of cameras needs an ID per device from the first boot, and that ID belongs in filenames, hostnames, and logs.

One model, per-store numbers

Grading needs physical units. The rim should be 13 to 25 millimeters wide, and ingredient weight is estimated from mask area. Each store's camera hangs at a different height and angle, so a pixel means something different in every store.

I kept one model and moved the per-store differences into configuration. The recipe file stores pixels_per_cm and pixels_per_gram for each store, and the grader falls back to defaults (40 pixels per centimeter and 450 pixels per gram) for any store without its own values:

def get_store_calibration(db, store_id=None):
    cal = db["calibration"]
    default = cal["default"]
    store_cal = cal.get("stores", {}).get(store_id, {})
    return {
        "pixels_per_gram": store_cal.get("pixels_per_gram", default["pixels_per_gram"]),
        "pixels_per_cm": store_cal.get("pixels_per_cm", default["pixels_per_cm"]),
    }

A helper script, calibrate_store.py, computes the values from a photo of a pizza with a known diameter or a weighed portion of one topping. Some ingredients also get their own conversion, because a pixel of thin tomato slice weighs far less than a pixel of chicken.

Here's the honest part: the tooling existed, but I never made calibration a required step. A store without its own values falls back to one default conversion, which can't be right for cameras at different heights.

If I built it again, calibration would be part of installation. The Pi setup wizard already asks for the store identity. It should also ask for a calibration photo, and the grader should refuse to report grams for an uncalibrated store instead of falling back without a warning.

One threshold doesn't fit every class

When the model learned new toppings, their detections on real camera images came in at confidences of 0.60 to 0.68. The global threshold was 0.75, so those detections were filtered out without any warning. With only the surviving toppings to go on, the recipe matcher graded multi-topping pizzas as single-topping recipes.

The fix was a confidence threshold per class, stored in the same configuration file. The values in my configuration range from 0.3 for air bubbles to 0.75, the default that pepperoni keeps because it's the best-trained class. A model whose classes saw very different amounts of training data needs per-class thresholds from the start.

Corrections are training data only if you keep them that way

The dashboard lets a reviewer flag a pizza and correct its recipe, size, and ingredient counts. Every correction is appended to a per-store pizza_corrections.json with the user, a timestamp, the old and new recipe, the old and new score, and the change per ingredient. Reviewers can also attach training flags such as bad shape or excess bubbling.

The retraining loop around that worked like this:

  1. Pre-label new images with the current model, and correct the labels in CVAT.
  2. Write 12 augmented variants per image, and train on a Colab GPU.
  3. Run compare_models.py, which grades the same test images with the old and the new model and exits with an error when the mean score drops by more than 5 points.
  4. Run validate_grading.py, which runs 125 checks against a saved baseline that records the model hash.

The gap sits between the corrections log and step 1. Corrections never turned into labels automatically. A diff that says pepperoni went from 12 to 14 doesn't say where the two missed slices are, so every round of retraining went back through CVAT by hand. Next time, a correction would queue the image for annotation with the model's pre-labels attached, and the corrections log would produce an accuracy figure per store, so I'd know which camera needed attention first.

Small operations mistakes

Several problems came from a few lines of shell:

  • Pulling the whole bucket. The server's cron job pointed rclone copy at the entire bucket every 15 minutes, including folders the grader never needed. Scoping the pull to new date folders is the better default.
  • A guard that never fires. The setup script checks for an existing cron line by searching for rclone sync wasabi, but the line it installs says rclone copy wasabi. The check never matches, so every rerun of the script adds another copy of the job.
  • Sync versus copy. An earlier version used rclone sync, which deletes local files that aren't in the bucket. That included the JSON files the dashboard writes next to the images.

What I'd do differently

Here's the short list:

  1. Calibrate every store during installation, and refuse to report physical units without it.
  2. Profile memory per image on the target hardware from the first prototype.
  3. Put the device identity in every filename from the first capture.
  4. Store corrections in a form that converts into labels.
  5. Split training data by source image before augmenting, and keep a fixed held-out test set.
  6. Run the privacy model on the edge device.
  7. Sync incrementally, and test that setup scripts are safe to rerun.

The part that worked

Using one model for every store kept deployment simple. Store-specific values were designed to live in configuration rather than in separate weights, and grading runs centrally, so a retrained model reached every store with one file copy to the server. The problems came from the steps I treated as setup chores. In a system like this, those steps are part of the product.
